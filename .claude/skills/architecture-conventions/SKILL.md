# Архітектурні конвенції проєкту

Цей файл — джерело правди щодо вже прийнятих архітектурних рішень.
Звіряйся з ним перед пропозицією нової системи чи компонента.

**Як користуватись:**

- Перед тим як писати код або пропонувати дизайн — перевір, чи рішення вже
  зафіксоване тут. Якщо так, дотримуйся його, а не вигадуй альтернативу.
- Якщо пропозиція суперечить конвенції — не мовчи: назви конкретний пункт,
  з яким є конфлікт, поясни чому, і дай користувачу вирішити.
- Якщо тема тут не покрита — це нове рішення. Запропонуй варіант у стилі
  наявних конвенцій і, після узгодження, **онови цей файл**.
- Розділ "Що свідомо відкладено" — не чіпати без явного запиту користувача.

## Мова коду: коментарі й логи — виключно англійською

Усе, що лишається **всередині коду**, пишеться англійською, без винятків:

- коментарі (`//`, `/* */`) і XML-doc (`<summary>`, `<param>`, `<remarks>`)
- рядки в `Debug.Log` / `LogWarning` / `LogError` та будь-якому іншому логуванні
- повідомлення виключень, `Assert`-описи, назви в `Profiler`-семплах
- текст debug-оверлеїв та редакторних `MenuItem`/діалогів
- імена типів, полів, методів і файлів (як завжди в C#)

Спілкування з користувачем у чаті, цей файл і документація — лишаються українською.
Правило стосується саме вмісту репозиторію.

**Чому:** код читають інструменти й люди поза цим контекстом — стектрейси в
Unity Console, дифи в рев'ю, пошук по помилці в інтернеті, майбутні
контриб'ютори. Змішана мова також ламає пошук по коду: половина термінів
кирилицею, половина латиницею. Один код-бейс — одна мова.

При правці існуючого файлу з коментарями українською — перекладай їх на
англійську принагідно, а не лишай упереміш.

## Загальний опис проєкту

Top-down co-op action-roguelike у стилі Path of Exile 2 / Diablo-like.
Гравці (2-4 у коопі) рухаються по процедурному данжу, відкривають сундуки,
отримують екіпіровку, використовують скіли з модифікаторами (chain, AOE,
fork, multicast), б'ються з товпами ворогів. Мультиплеєра поки немає,
але вся архітектура закладається під нього з самого початку.

## Технічний стек

- Unity 6000+ / Entities 1.x (DOTS: ECS, Jobs, Burst)
- NavMesh (Unity.AI.Navigation) для pathfinding ворогів
- VFX Graph (не Shuriken) для масових ефектів
- **Input System (новий)** — legacy `UnityEngine.Input` не використовується
- **Addressables** для рантайм-завантаження ассетів
- Майбутній мультиплеєр: Netcode for Entities (NFE), host-based (listen server)
- **Без DI-фреймворків** (без Zenject/VContainer)
- **Без static/singleton класів у C#** взагалі

## Завантаження ассетів: Addressables

Усе, що вантажиться **в рантаймі**, йде через Addressables — префаби,
ScriptableObject-и, сцени, VFX, аудіо, іконки UI.

- Ніяких `Resources.Load` і папки `Resources/` — вони тягнуть усе в
  білд без контролю і не дають вивантажити
- Ніяких прямих `[SerializeField] GameObject` на важкі префаби, які
  потрібні не завжди: таке посилання завантажується разом зі сценою,
  навіть якщо об'єкт не знадобиться жодного разу
- Використовувати `AssetReference` / `AssetReferenceGameObject` замість
  прямих посилань

### Окремий модуль завантаження — обов'язково, з першої ж потреби

Щойно в проєкті виникає перша реальна потреба щось завантажити через
Addressables — **спочатку створюється окремий модуль завантаження і
звільнення ресурсів**, і вже він використовується. Не «поки що
викличемо `Addressables.LoadAssetAsync` тут, а винесемо потім».

- Прямі виклики `Addressables.LoadAssetAsync` / `InstantiateAsync` /
  `Release` по всьому коду — заборонені. Викликати їх має право лише
  сам модуль
- Модуль володіє всіма хендлами й веде їхній облік; зовнішній код
  отримує ассет і запитує звільнення, але не тримає `AsyncOperationHandle`
- Час життя ресурсів прив'язується до явних областей (сцена, забіг,
  екран меню), а не до випадкового `OnDestroy` того об'єкта, який
  першим щось попросив
- Модуль — звичайний клас з `Initialize()` через `GameBootstrap`, як і
  решта сервісів. Без static, без DI-контейнера

**Чому саме так.** Розкидане завантаження ламається тихо і пізно: хендл,
звільнений двічі, і хендл, не звільнений жодного разу, обидва не дають
помилки в момент помилки. Витік видно як зростання пам'яті через
півгодини гри, а подвійне звільнення — як зникнення чужого ассета в
іншій системі. Одна точка входу перетворює це з полювання на баг у
перевірку одного файлу. Друга причина: коли з'явиться мережа, набір
ресурсів на клієнті й на хості різний, і місце, де це задається, має
бути одне.

**Важливий виняток — ECS-префаби.** Сутності ворогів, projectile-ів,
пікапів потрапляють у світ через **бейкінг** (authoring + `Baker` у
SubScene), а не через Addressables. Там `GetEntity(prefab, ...)` — це
посилання часу бейкінгу, і воно правильне. Addressables у DOTS-частині
стосується завантаження самих SubScene/секцій, а не окремих
entity-префабів. Не переписуй бейкери на Addressables.

Практичний поділ:

| Що | Механізм |
|---|---|
| Entity-префаб (ворог, снаряд, орб) | Baker, `GetEntity` |
| Секція данжу / SubScene | Addressables (або `SceneSystem` для entity-сцен) |
| GameObject-префаб UI, VFX, звук | Addressables |
| Конфіги (`SkillDefinition`, `LootTable`) | Addressables, якщо їх багато і вони потрібні вибірково |

## Інпут: тільки новий Input System

- `UnityEngine.Input`, `KeyCode`, `Input.GetAxis`, `Input.mousePosition`,
  `Input.mouseScrollDelta` — **заборонені**. Проєкт працює з
  `activeInputHandler` у режимі New; будь-який legacy-виклик кине
  виняток у рантаймі, а не впаде на компіляції
- Читання інпуту зосереджене в одному місці (`PlayerInputReader`), яке
  віддає намір (`PlayerMoveIntent`) у світових координатах. Решта коду
  не знає ні про пристрої, ні про камеру — це та сама межа, що й для
  ECS-систем ворогів, і той самий шов під майбутню мережу
- Кросплатформність закладається **біндами, не гілками в коді**: одна
  дія має прив'язки для кількох родин пристроїв. Нова платформа має
  бути рядком біндингу
- `<Pointer>/position` замість `<Mouse>/position` — одна прив'язка
  покриває мишу, стилус і тач
- Дії, створені в коді, володіють нативними ресурсами — `Dispose()`
  в `OnDestroy`
- Інпут виду (зум, поворот камери) тримати окремо від ігрового наміру:
  він локальний і ніколи не має потрапити в те, що поїде на сервер

Поточний стан: дії будуються в коді в `CreateActions()`, без
`.inputactions`-ассета. Це свідомий розмін на користь того, щоб інпут
працював одразу, без ассета, який треба тримати в синхроні. Перехід на
ассет, коли знадобиться UI для перепризначення клавіш, — правка одного
файлу.

## Ключовий архітектурний принцип: server-authoritative-ready

Уся ігрова логіка (вороги, скіли, шкода, лут) будується так, ніби її вже
зараз може виконувати виключно сервер/хост, навіть у single-player режимі:

- ECS-системи логіки НЕ звертаються напряму до `Input`, `Camera.main`,
  чи UI — тільки до даних через компоненти/сінглтони
- Розділяти компоненти на:
  - **"видимі" / presentation** (Position, Rotation, анімаційний стан,
    HP-бар) — майбутні кандидати на `GhostComponent` в NFE
  - **"логічні" / authoritative** (AI-рішення, шлях, кулдауни скілів,
    RNG-роли луту) — залишаються суто серверними, не реплікуються
    напряму (наприклад, `PathPoint` buffer НЕ реплікується — клієнт
    знає лише позицію+напрямок)
- Дії гравця (відкрити сундук, кастувати скіл) моделювати як
  "запит на дію" (клієнт) → "результат дії" (сервер), навіть коли
  клієнт і сервер — той самий процес зараз

## ECS-конвенції

- Доступ до глобальних даних (позиція гравця, налаштування) — через
  **singleton-компоненти** (`SystemAPI.GetSingleton<T>()`), НЕ через
  C# static
- Приклад: `PlayerPositionSingleton` — тепер розширений під кількох
  гравців (список `PlayerId` + позиція кожного); `ChaseTarget` ворога
  вибирає найближчого/найагресивнішого гравця зі списку, а не хардкод
  на одного гравця
- Time-slicing для дорогих операцій (pathfinding, масові AOE/chain
  розрахунки) — ліміт N операцій за кадр як параметр, що виноситься
  в інспектор
- `DamageEvent` — буфер-компонент **на цілі**, куди всі системи шкоди
  пишуть наміри, а `DamageResolutionSystem` застосовує це фінально.
  Буфер саме на цілі, а не глобальний потік подій: сто снарядів по ста
  ворогах пишуть у сто різних місць, і резолв паралелиться по сутностях
  безкоштовно. Подія несе й радіус вибуху — бо саме той удар, який убив,
  вирішує, чи вибухне тіло, і так резолву не треба шукати, який скіл
  з якими супортами це зробив
- Separation/уникнення зіткнень між ворогами — через spatial hashing
  (`NativeParallelMultiHashMap`), не O(n²) перебір
- Object pooling для VFX-інстансів і projectile-entity — не
  Instantiate/Destroy напряму

## MonoBehaviour / UI-шар конвенції

Без static, без DI-контейнера. Замість цього:

1. **ScriptableObject як shared state / event channel** — основний
   підхід для даних, які читаються з багатьох місць (стан гравця,
   event-канали типу `OnWaveCleared`, `OnPlayerDied`). Патерн:
   "ScriptableObjects as Architecture" (Ryan Hipple)
2. **Явний `Initialize()` через один `GameBootstrap`-скрипт** — для
   сервісних класів з поведінкою (AudioManager, SceneLoader). Bootstrap
   створює/знаходить інстанси і викликає `Initialize()` в правильному
   порядку
3. Дані типу `LootTable`, `SkillDefinition`, `ItemDefinition` — теж
   ScriptableObject, консистентно з підходом вище

**Нюанс:** ScriptableObject — asset у пам'яті, спільний для всіх
інстансів у межах одного процесу. Для реального білда (кожен клієнт —
окремий процес) це нормально. При локальному тестуванні мультиплеєра
в одному Editor-інстансі (напр. через ParrelSync) можливі конфлікти
стану — враховувати при переході на NFE.

## Процедурна генерація данжу

Рішення прийняті й реалізовані — не переобговорювати без запиту.

- **BSP, а не template-based.** Шаблонні кімнати вимагали б бібліотеки
  префабів і, за правилом вище, модуля завантаження Addressables ще до
  того, як по першій кімнаті можна пройтись. BSP не потребує нічого,
  крім чисел, і дає зв'язність безкоштовно: дерево гарантує, що кожна
  кімната досяжна від входу, і ізольованих кишень не буває
- Типи кімнат: `Entrance`, `Transit`, `Combat`, `Treasure`, `Boss`.
  Boss — найглибша кімната за кількістю переходів від входу, treasure —
  у тупиках (`Degree == 1`), решта ділиться між бойовими й прохідними
  за часткою з конфігу
- **Генерація — чиста функція від seed.** Всередині генератора заборонені
  `UnityEngine.Random`, час, номер кадру й порядок обходу хеш-контейнерів.
  Сортування — з тай-брейком по id, щоб нестабільний сорт давав однаковий
  результат на різних машинах. Данж не реплікується взагалі: по мережі
  піде seed, кожен клієнт побудує ідентичний поверх сам
- **Seed народжується в одному місці** — `DungeonDirector.ResolveSeed()`.
  У коопі його викличе лише хост, решта передасть отримане число прямо
  в `BeginRun`
- **NavMesh пікається в рантаймі, асинхронно.** `BuildNavMeshAsync` у
  `com.unity.ai.navigation` 2.0.14 **не існує** — асинхронний шлях це
  `UpdateNavMesh(data)`, якому потрібен уже створений `NavMeshData`.
  Серфейс збирає **тільки дітей**: `CollectObjects.All` запік би капсули
  гравця й ворогів як перешкоди
- **Фази забігу гейтять усе інше.** Поки `DungeonRunState.Phase` не
  `Ready`, точки спавну не створюються й кімнати не вмикаються — ворог
  на неготовому navmesh просто пройде крізь стіни
- Геометрія — бокси-примітиви з колайдерами, злиті в горизонтальні
  прогони по рядках. Один об'єкт дає і колізію, і видиму поверхню, і
  джерело для бейку; без злиття поверх 64×64 — це чотири тисячі об'єктів
- Кімнати живуть у `DynamicBuffer<DungeonRoomElement>` на сінглтоні забігу,
  а не окремими сутностями: їх десяток і їх щокадру перебирають разом

### Активація кімнат — той самий поділ, що в pathfinding

`RoomOccupancySystem` (Burst, міряє, хто де стоїть) → `RoomActivationSystem`
(вирішує `Dormant → Active → Cleared` і кладе ордер) → `WaveSpawnSystem`
(виконує). Спавнер не знає про данж: він читає `WaveSpawnOrder`
(`RoomId` + `Count`), а точки спавну фільтруються по `SpawnPoint.RoomId`.
Тому та сама система обслуговує і процедурний поверх, і ручну арену.

## Сундуки, лут і взаємодія

Рішення прийняті й реалізовані — не переобговорювати без запиту.

- **Взаємодія — це два різні типи й дві різні системи.** Клієнт кладе
  `InteractionRequest` (гравець + позиція, **без цілі**); хост у
  `InteractionResolveSystem` обирає найближчу доступну ціль у її радіусі
  й вмикає на ній `InteractionTriggered`. Клієнт, що називає ціль сам,
  може назвати сундук на іншому кінці поверху
- **`InteractableTag` — enableable, і це і є прапорець доступності.**
  Відкритий сундук і піднятий предмет вимикають власний тег і зникають
  з запиту резолвера. Резолвер не знає, які бувають види взаємодій
- **Резолвер вирішує ХТО і З ЧИМ, ніколи — що це означає.** Сенс дає
  система відповідного виду: `ChestInteractionSystem`, `ItemPickupSystem`.
  Важіль, двері чи підняття збитого напарника резолверу нічого не коштують
- **Гонку за сундук виграє перший.** У межах кадру — бо ціль, уже
  зайнята попереднім запитом у черзі, пропускається; далі — бо сундук
  перестає бути interactable у мить, коли його забрали
- **Рол луту дворівневий:** спершу рідкість за вагами, потім предмет
  усередині рідкості. Ваги предметів безпосередньо — це коли тридцять
  common-предметів ховають один legendary, і число біля «Legendary»
  перестає означати те, що написано. Рідкості, для яких у таблиці нема
  предметів, занулюються при бейку
- **Таблиці — у блоб**, не в managed-посилання на SO: джоба не читає
  ассет, і хост має ролити з даних, які належать йому
- **Дроп — сутності у світі, ніколи не одразу в інвентар.** Це найдешевша
  відповідь на «кому дісталось»: обидва гравці бачать, як предмети падають,
  і хтось підходить. Нема ні правила розподілу, ні таймера, ні предмета
  чинного суперечці
- **Інвентар — буфер `InventoryItem` на сутності персонажа.** Він займає
  місце тимчасового `CollectedItem`, як і планувалось; `ItemPickupSystem`
  так само пише «цей гравець тепер володіє цим предметом», просто в інше
  місце
- **Предмет народжується `AtRisk`.** Підняття не робить його безпечним —
  безпечним його робить вихід з данжу, за правилом [ItemRiskState] вище
- **Id предмета — FNV-1a від назви**, не `string.GetHashCode`: той
  рандомізований на процес, і два гравці захешували б той самий предмет
  по-різному

## Екіпіровка та стати

Рішення прийняті й реалізовані — не переобговорювати без запиту.

- **У гравця є сутність у ECS** — `PlayerCharacter`. Вона **виводиться**
  з буфера позицій (`PlayerCharacterRegistrySystem`), а не публікується
  мостом: буфер уже є списком «хто грає», тож гравець, що підключився,
  отримує персонажа сам собою
- **Позиція і персонаж свідомо не злиті.** `PlayerPositionElement` —
  пласкі дешеві дані, які щокадру читають джоби ворогів; персонаж — це
  лист із інвентарем. Злиття поклало б буфер інвентаря в гарячий шлях
  кожного ворога на поверсі
- **Слоти — буфер, індексований `EquipmentSlot`**, а не чотири поля.
  Слоти — саме те, що найімовірніше зростатиме (персні, чоботи, друга
  зброя), і кожен новий має бути значенням enum, а не зміною схеми плюс
  чотирма системами, які забули прочитати нове поле
- **Формула — PoE:** `final = (base + flat) * (1 + increased)`, де всі
  increased до одного стата спершу **додаються** і множаться один раз.
  Два +50% дають 2x, а не 2.25x. Саме заради цієї різниці два види
  модифікаторів взагалі розділені
- **Кеш статів — це `StatsDirty`, а не збережений результат.**
  `PlayerStatsSystem` бере персонажів з піднятим прапорцем, тож у кадр,
  коли ніхто нічого не міняв, він перебирає нуль сутностей. Немає стану,
  який хтось має не забути інвалідувати
- **Слот бере хост із визначення предмета, а не з запиту.** Клієнт, який
  міг би обрати слот, надів би дворучний меч як шолом. Так само перевіряється,
  що предмет справді в інвентарі того, хто просить
- **UI не дублює стан.** `InventoryUI` щоразу читає персонажа з ECS і
  малює прочитане; кліки лише додають `EquipRequest`. Панель фізично не
  здатна показати надітим те, що хост відхилив, бо їй нема де це тримати.
  Перемальовується лише коли змінилась сигнатура (версія статів + інвентар)
- **`ItemBlob` не можна копіювати** — усередині `BlobArray` афіксів, а
  його зміщення відносне до власної адреси. Тільки `ref`. Тому й пошук
  живе методом на компоненті `ItemDatabase`, а не на блобі

### Слоти: десять, дві руки й два персні

- **Слот їде в запиті й перевіряється, а не ігнорується.** Це свідома зміна
  правила «слот бере хост із визначення предмета»: перстень підходить у дві
  руки, і яка саме — вирішує гравець, а не предмет. Перевірка йде по масці
  `ItemBlob.AllowedSlots`, тож клієнт може назвати слот, але не будь-який
- **Маска виводиться з одного авторського слота, а не пишеться списком.**
  `EquipmentSlots.AllowedMask` розкриває Ring1 у пару. Список на ассеті
  означав би перстень, який забули позначити другим слотом; правило в
  одному методі означає, що третій слот перснів — це один рядок
- **Кожен запит — одна транзакція.** `ToSlot`, `Auto`, `Unequip`,
  `SwapSlots` — одна система, бо дворучна зброя рухає три предмети одразу
  й проміжний стан, у якому в обох руках щось є, не має існувати. Усе, що
  може не вдатись, перевіряється до першого запису, а єдине спекулятивне
  очищення сітки скасовується на кожному шляху, що каже «ні»
- **`SwapSlots` не проходить через сумку** — і тому працює, коли в сумці
  нема місця. Перстень з руки в руку через зняття й вдягання відмовляли б
  повній сумці в тому, що її взагалі не стосується
- **Блокування лівої руки виводиться щоразу**, а не зберігається прапорцем:
  збережений залишився б піднятим після того, як дворучну зброю зняли
- **`EquipResult` існує заради відмов.** Відмова лишає світ незмінним, тож
  без черги результатів гравець бачив би, як предмет просто стрибає назад.
  «У сумці нема місця» — це різниця між правилом і багом

## Grid-інвентар

Реалізовано — не переобговорювати без запиту.

- **Носимий предмет — сутність, узята з пулу луту.** Та сама, що лежала на
  підлозі: підбір не повертає її в пул, а лишає жити з піднятим `ItemStored`.
  Свідомий вибір проти буфера `InventoryItem`, який тут стояв раніше:
  `ItemGridPlacement` мусить висіти **на предметі**, і та ж сама зміна дає
  ідентичність екземпляра, якої однаково потребуватимуть роляні афікси
- **Вільний для пулу = два опущені прапорці.** `InteractableTag` (не на
  підлозі) і `ItemStored` (нічий). Розмір пулу став стелею на всі предмети,
  що існують одночасно — той самий розмін, що `MaxAlive` для ворогів
- **Контейнер — окрема сутність**: `InventoryGridComponent` + буфер
  `InventoryCell` + `ContainerOwner`. Сумка, стеш і скриня на землі — один і
  той самий набір з різними числами. Спільний стеш буде контейнером **без**
  власника, і це окрема розмова, а не наслідок забутого поля
- **Клітинка зберігає `Entity`, і предмет пише себе в кожну, яку вкриває.**
  Питання «чи вільний цей квадрат» — одне читання масиву, а не пошук по
  списку предметів з їхніми розмірами. Ціна — предмет трапляється в буфері
  кілька разів, тому ніхто не рахує предмети, рахуючи клітинки
- **Одна система на розміщення, не три.** `InventoryRemovalSystem` і
  `AutoPlaceSystem` — це режими запиту (`Exact` / `Auto` / `Remove`), бо
  переміщення мусить бути неподільним: через дві системи є кадр, у якому
  предмет не існує ніде, і відмова після зробленого прибирання втрачає річ.
  Той самий аргумент, що й про модифікатори скілів нижче
- **`EquipmentSystem` рухає сітку сам**, а не через запит — з тієї ж причини.
  Він викликає `GridFit`, а не повторює його: правила лишаються в одному
  файлі, просто в нього два законні власники
- **Чистити ДО перевірки, і вміти покласти назад.** Інакше предмет стикається
  сам із собою. Відновлення читає `IsRotated` із записаного розміщення —
  клітинки знають, що предмет там був, і не знають, як він лежав
- **Поворот — властивість предмета, не дефолт.** `CanRotate` за замовчуванням
  вимкнений і зануляється для квадратних предметів. Автопошук місця пробує
  повернутий варіант **лише** якщо прямий не вліз
- **First-fit, а не best-fit.** Best-fit запакував би щільніше, але
  переставляв би те, чого гравець не просив. Інвентар, який сам себе
  перекладає, гірший за інвентар, який заповнився
- **UI рахує передбачення тим самим `GridFit`, read-only.** Друга реалізація
  колись розійшлася б з відповіддю, а зелена клітинка з наступною відмовою
  гірша за відсутність підсвітки. Запит іде **завжди**, хоч би якого кольору
  була клітинка: клієнт, що не питає, бо сам вирішив «не вийде», — це клієнт,
  чиї баги виглядають як баги хоста
- **Поки панель відкрита, касти й взаємодія не публікуються.** Перетягування —
  це ЛКМ, і перший скіл теж. Прапорець іде з панелі в `PlayerActionPublisher`
  делегатом через `GameBootstrap` — панель нікуди не тягнеться сама

## Скіли та модифікатори

Модель PoE (skill + support gems). Реалізовано — не переобговорювати
без запиту.

- `SkillDefinition` (SO): базовий ефект (`Projectile`, `MeleeArc`,
  `AreaBurst`, `ChainBolt`), урон, кулдаун, радіус, дуга, дальність
- `SkillModifier` (SO): супорти вставлені **в скіл**, а не в персонажа —
  той самий Chain у двох скілах означає різне, і в цьому вся суть моделі
- Конвеєр: `SkillCastSystem` → `SkillProjectileSystem` / `SkillAreaSystem`
  → `SkillHitSystem` → `DamageResolutionSystem` → `DeathReactionSystem`

### Модифікатори — згортка при касті, а не система на кожен

**Свідомий відступ від початкового плану цього файлу.** Більшість
супортів міняє, скільки всього існує і якого воно розміру — це рішення
до того, як щось з'явилось, і система, що читає `DamageEvent`, той
момент уже проґавила. Система на модифікатор дала б з десяток систем,
які майже щокадру не перебирають нічого, а відповідь на «звідки це
число» була б розмазана по всіх.

Тому `SkillDatabase.Resolve` згортає супорти в `ResolvedSkill` **один
раз на каст**, і далі все працює з готовими числами. Те, що справді
належить далі по конвеєру, там і лишилось — але як поведінка, не як
система-модифікатор:

- **Chain** — на стадії влучання (`SkillHitSystem`), із затримкою між
  стрибками зі скіла й списком уже відвіданих цілей у самому `PendingHit`
- **Fork** — на удар снаряда (`SkillProjectileSystem`): два нових снаряди
  з на один менше
- **ExplodeOnKill** — на смерть (`DeathReactionSystem`)

Снаряд у польоті несе все, чим резолвиться його влучання, і нічого не
знає про скіл, який його випустив — тому скіл можна перекастувати чи
змінити, поки він летить.

### Композиція скілів — супорт-тригер (варіант C, реалізовано)

`SkillModifier` з видом `TriggerOnHit` носить посилання на інший
`SkillDefinition`. Коли скіл-носій **приземляється**, тригер ставить
`PendingCast` у чергу, і `SkillCastSystem` розбирає її поруч із запитами
гравця. «ЛКМ пускає снаряди, що роблять Q» — це перетягування одного
ассета в сокет.

Чому саме супорт, а не поле на скілі: у проєкті вже діє модель «усе, що
змінює скіл, — це супорт». Один тригер перевикористовується в кількох
скілах, і `SkillDefinition` не росте полями під кожну комбінацію.

Правила, які тримають це в межах:

- **Раз на екземпляр ефекту, ніколи — раз на влучене тіло.** Один удар
  снаряда, один вибух, один змах. Інакше площа на сорок ворогів дала б
  сорок кастів, і кількість залежала б від тісноти в кімнаті
- **Ланцюг не тригерить.** Він — один ефект, що торкається кількох тіл;
  тригер на кожен стрибок повернув би залежність від натовпу
- **`Depth` у `PendingCast` — єдиний запобіжник від циклу.** Два скіли,
  що тригерять один одного, авторуються випадково за секунду. `MaxDepth`
  у `SkillDatabaseAuthoring`; зростання **експоненційне**, тож 2 — це не
  «поки що мало», а свідома стеля
- **Тригер не бере кулдаун і не перевіряє, чи скіл досі екіпірований.**
  Це наслідок; момент, коли його можна було не допустити, вже минув
- **`-1`, а не 0, означає «нічого не тригерити».** Нуль — валідний індекс
  скіла, тож поле проставляється явно скрізь, де створюється снаряд
  або площа
- Тригерований каст іде **наступним кадром** (черга розбирається до того,
  як снаряди рухаються). Шістнадцять мілісекунд, яких не видно, замість
  системи касту, що працює двічі за кадр

### Варіант D — дерево ефектів (розглянуто, відкладено)

Скіл як граф вузлів: кожен вузол — ефект зі своїми параметрами й дітьми
на подіях «влучив / убив / згас». Виразність максимальна, а модель
«скіл + супорти» стає її окремим випадком.

Не зроблено свідомо: це переписування блоба і всіх стадій конвеєра, а
головне — таким деревом ніхто не авторуватиме без кастомного інспектора,
тож ціна не в самому графі, а в редакторі до нього. Повертатись сюди має
сенс тоді, коли супорт-тригера почне бракувати — тобто коли знадобляться
різні наслідки для «влучив» і «вбив» в одному скілі. Поточна модель це
вже майже вміє: `ExplodeOnKill` — і є той другий тип події, просто
захардкоджений.

### Черги між стадіями — такі самі буфери-ордери, як скрізь

`PendingHit` і `PendingArea` на сінглтоні. Площа не має привілейованого
шляху до шкоди: вона виробляє такі самі влучання, як один снаряд. Тому
вибух може спричинити що завгодно й зачепити кого завгодно, і жодна
стадія не знає, хто її наповнив.

**Вибух при вбивстві мусить занулити власний радіус** у черзі. Без цього
одного рядка одне вбивство детонує весь поверх.

**Multicast — це один кулдаун і кілька ефектів**, а не кілька кастів.

## "Вау"-ефекти (масові вбивства)

Реалізовано — не переобговорювати без запиту.

### Один шов: черга `VfxEvent`

Системи симуляції оголошують, **що сталося** (`ChainLink`, `Explosion`,
`Death` — позиція, колір, величина) і ніколи не дізнаються, як це виглядало.
`VfxPresenter` читає чергу, малює й назад не пише. Наслідки, заради яких
це так:

- жодна система не може чекати на презентацію;
- білд без презентера грається ідентично, просто тихо;
- у мережевому білді ці події **виводяться на клієнті** зі стану, який
  у нього вже є, а не реплікуються. Тому черга живе на власній сутності,
  окремо від авторитетних черг бою — відповідь на «чи це реплікується»
  стає властивістю того, на якій сутності воно лежить

### Чим малюється зараз

**VFX Graph у проєкті нема, і `.vfx` — це серіалізований граф**, який не
створити з коду. Замість нього — пул `LineRenderer` на дві форми, яких
цій грі й вистачає: лінія ланцюга (дві точки) і кільце ударної хвилі
(коло точок, що розходиться). Обидві згасають **шириною, а не альфою**,
тож ефект не залежить від того, чи прозорий матеріал лінії.

Пул фіксований: після `Initialize` нічого не створюється, а коли всі
лінії зайняті — забирається найстаріша. Ефект, що спрацьовує десятки
разів на секунду, не має права алокувати.

Заміна на VFX Graph — це переписати чотири методи `Handle` у презентері.
Нічого вище за течією не зміниться.

### Завіса екрана

Реалізовано — не переобговорювати без запиту.

- **Непрозорість — стан симуляції.** `CurtainState.Opacity` живе в ECS і
  рухається `CurtainSystem`; презентер лише малює. Причина не в чистоті:
  на завісу **чекають** — «зносити поверх, коли екран чорний» мусить бути
  питанням, яке ставить система, а не MonoBehaviour, бо на сервері без
  графіки той самий момент має настати в той самий час
- **Запит — черга, і останній перемагає.** Завіса це рівень, а не подія:
  найновіший намір і є поточний. Дві системи, що хочуть екран в одному
  кадрі, отримують правило замість гонки
- **Unscaled-час і лінійний рух.** Hit-stop не має права розтягувати фейд;
  згладжування ховає прибуття, а на `IsCovered` хтось чекає
- **`IsCovered` — це `>= 0.999`, а не `== 1`.** Фейд, що спинився на
  сотій долі, лишив би систему чекати на різницю, якої не видно

### Звук

Реалізовано — не переобговорювати без запиту.

- **Той самий шов, що `VfxEvent`, і власна сутність.** Система оголошує
  «тут сталося оце»; який це кліп і чи його взагалі чути — не її справа.
  У мережевому білді ці події **виводяться на клієнті**, не реплікуються
- **Дві черги, не одна.** VFX і звук ріжуть по-різному: сорок смертей — це
  сорок тіл і приблизно один звук. Спільний буфер означав би, що кожен
  презентер щокадру перебирає чужі події
- **`AudioCue` — маленький фіксований словник, не посилання на кліп.**
  Джоба не тримає managed-ассет, байт реплікується, а який з чотирьох
  хрипів програти — питання до конфігу, а не до системи, що вбила
- **Три бюджети, бо без них ланцюгова реакція дає 120 звуків/сек**: на кадр
  глобально, на кадр для кожного cue, і мінімальний інтервал. Виняток той
  самий, що в тряски: помітно гучніший екземпляр проходить
- **Пул `AudioSource`, розмір = стеля на одночасні звуки.** Коли всі зайняті,
  забирається найстаріший — той самий розмін, що в пулі ліній
- **Просторовість — властивість cue, не події.** Клік у меню не має
  позиції й ніколи не матиме; поле на події дало б двом викликам
  посперечатись про один звук

### Cinemachine не використовується

Пакет встановлений, але камера в проєкті власна: 50 рядків фіксованого
кута без brain, virtual camera й блендів. Перехід на Cinemachine заради
одного impulse означав би замінити весь риг, щоб отримати тряску,
яка коштує п'ятнадцять рядків. Тряска й zoom punch — методи на самому ригу.

### Смерть — не миттєве знищення

`EnemyTag` **enableable**. Тіло, що догорає, все ще сутність, але вже не
ворог: один запис вимикає прапорець, і воно випадає з переслідування,
підрахунку, наведення снарядів і з умови «кімната зачищена» — бо запити
й так фільтрують за enabled-станом. Далі `DeathFadeSystem` стискає масштаб
і темнить колір, і аж тоді знищує. Dissolve-шейдера нема: масштаб і
per-instance колір уже є, коштують нуль і несуть те саме прочитання.

### Правила відчуття

- **Hit-stop мусить уміти скасувати себе.** `Time.timeScale` — глобал;
  зупинка, що не завершилась, лишає гру на 5% швидкості без підказки чому.
  Масштаб запам'ятовується на вході, `Release()` викликається з `OnDisable`,
  а повторний запит **подовжує**, а не вкладається
- **Усе про відчуття — в unscaled-часі.** Тряска й лінії під час hit-stop
  мають рухатись, інакше завмирає саме те, заради чого зупинку робили
- **Що таке «масове вбивство» — рішення презентації, не симуляції.** Поріг
  і вікно живуть у презентері; жодна система не рахує вбивства заради камери
- Тряска накопичується з межею: двісті смертей в один кадр не мають
  викидати камеру за межі кімнати

## Порядок розробки (заведений принцип)

Кожна нова велика система впроваджується ітеративно, невеликими кроками,
з перевіркою продуктивності (FPS з 100+ ворогами) перед переходом до
наступного кроку. Не намагатись реалізувати все одним заходом — спочатку
план/структура файлів, узгодження, потім код частинами.

## Прогресія поверхів данжу (floor progression / risk-reward descend)

- Data-driven через `DungeonFloorConfig` (SO): FloorIndex,
  EnemyDifficultyMultiplier, LootRarityWeights, IsBossFloor,
  RoomCountRange, EnemyDensityMultiplier — складність і лут
  масштабуються множниками, а не хардкодяться на кожен поверх
- Boss floors: `BossEncounterConfig` (SO), boss-кімната блокується
  (`BossRoomState`: Locked/InProgress/Cleared) до перемоги; інтервал
  між боссами — параметр конфігу, не константа в коді

### Смерть/лут — трьохстанова модель (Alive → Downed → Dead), зафіксовано

Правило гри: кожен гравець відповідає лише за свій лут. Смерть
двофазна — спочатку "Downed" (можна відродити), і лише за timeout
(або team wipe) настає "Dead" з остаточною втратою лута.

- `PlayerLifeStateComponent`: enum `Alive/Downed/Dead` + `DownedTimer`
  + `MaxDownedDuration` + `RevivingByPlayer` (Entity.Null якщо ніхто
  не відроджує)
- `DownedStateSystem`: HP <= 0 і Alive → Downed, старт таймера
- `ReviveInteractionSystem`: живий гравець поруч утримує channeled-дію
  відродження; переривається при відході чи отриманні урону тим, хто
  відроджує
- `DownedTimeoutSystem`: таймер сплив без відродження → Dead →
  викликає `DeathResolutionSystem` ЛИШЕ для цього гравця (втрата
  лише його лута, не чужого)
- `TeamWipeCheckSystem`: усі гравці одночасно Downed/Dead (жодного
  Alive) → примусово всіх Downed → Dead, завершує забіг для команди.
  Сам видаленням лута не займається — викликає ту саму
  per-player `DeathResolutionSystem` для кожного, щоб не дублювати
  логіку

### Ризик предметів — `ItemRiskState`, а не `AcquisitionSource`

Ризику підлягає НЕ лише знайдене в підземеллі, а й усе, що гравець
взяв із собою з лобі на цей захід:

```csharp
public enum ItemRiskState
{
    Safe,     // лишається в PersistentStash, недоступне під час забігу
    AtRisk    // взяте на захід (з лобі АБО знайдене в данжі) —
              // втрачається при остаточній смерті (Dead) власника
}
```

При вході в данж екіпіроване з лобі позначається AtRisk. При Dead —
все AtRisk цього гравця видаляється. При успішному виході з данжу —
AtRisk → Safe (конвертація enum, без переносу між колекціями).

### Лобі-фаза

Окремий `LobbyState` перед стартом забігу — гравці екіпірують
персонажа (спорядження, зілля) з `PersistentStash` (Safe-інвентар).
Те, що екіпіровано на момент старту, стає AtRisk на час забігу.

### Кооп-специфічне рішення (закладено, НЕ конфігурований прапорець — рішення прийнято)

- Team wipe відбувається лише як наслідок того, що всі гравці
  досягли стану Dead (немає живого, хто міг би відродити) — не
  окремий bool-прапорець, а емерджентний результат Downed/Revive
  системи
- `DungeonRunState` (singleton, спільний для команди) розширити
  полями `IsRunActive` і `RunEndReason` (TeamWipe /
  AllExtractedSuccessfully), щоб UI та інші системи знали момент і
  причину завершення забігу
