## Мова коду: коментарі й логи — виключно англійською

Усе, що лишається **всередині коду**, пишеться англійською, без винятків:

- коментарі (`//`, `/* */`) і XML-doc (`<summary>`, `<param>`, `<remarks>`)
- рядки в `Debug.Log` / `LogWarning` / `LogError` та будь-якому іншому логуванні
- повідомлення виключень, `Assert`-описи, назви в `Profiler`-семплах
- текст debug-оверлеїв та редакторних `MenuItem`/діалогів
- імена типів, полів, методів і файлів (як завжди в C#)

Спілкування з користувачем у чаті, цей файл і документація — лишаються українською.
Правило стосується саме вмісту репозиторію.

**Чому:** код читають інструменти й люди поза цим контекстом — стектрейси в
Unity Console, дифи в рев'ю, пошук по помилці в інтернеті, майбутні
контриб'ютори. Змішана мова також ламає пошук по коду: половина термінів
кирилицею, половина латиницею. Один код-бейс — одна мова.

При правці існуючого файлу з коментарями українською — перекладай їх на
англійську принагідно, а не лишай упереміш.

## Загальний опис проєкту

Top-down co-op action-roguelike у стилі Path of Exile 2 / Diablo-like.
Гравці (2-4 у коопі) рухаються по процедурному данжу, відкривають сундуки,
отримують екіпіровку, використовують скіли з модифікаторами (chain, AOE,
fork, multicast), б'ються з товпами ворогів. Мультиплеєра поки немає,
але вся архітектура закладається під нього з самого початку.

## Технічний стек

- Unity 6000+ / Entities 1.x (DOTS: ECS, Jobs, Burst)
- NavMesh (Unity.AI.Navigation) для pathfinding ворогів
- VFX Graph (не Shuriken) для масових ефектів
- **Input System (новий)** — legacy `UnityEngine.Input` не використовується
- **Addressables** для рантайм-завантаження ассетів
- Майбутній мультиплеєр: Netcode for Entities (NFE), host-based (listen server)
- **Без DI-фреймворків** (без Zenject/VContainer)
- **Без static/singleton класів у C#** взагалі

## Завантаження ассетів: Addressables

Усе, що вантажиться **в рантаймі**, йде через Addressables — префаби,
ScriptableObject-и, сцени, VFX, аудіо, іконки UI.

- Ніяких `Resources.Load` і папки `Resources/` — вони тягнуть усе в
  білд без контролю і не дають вивантажити
- Ніяких прямих `[SerializeField] GameObject` на важкі префаби, які
  потрібні не завжди: таке посилання завантажується разом зі сценою,
  навіть якщо об'єкт не знадобиться жодного разу
- Використовувати `AssetReference` / `AssetReferenceGameObject` замість
  прямих посилань

### Окремий модуль завантаження — обов'язково, з першої ж потреби

Щойно в проєкті виникає перша реальна потреба щось завантажити через
Addressables — **спочатку створюється окремий модуль завантаження і
звільнення ресурсів**, і вже він використовується. Не «поки що
викличемо `Addressables.LoadAssetAsync` тут, а винесемо потім».

- Прямі виклики `Addressables.LoadAssetAsync` / `InstantiateAsync` /
  `Release` по всьому коду — заборонені. Викликати їх має право лише
  сам модуль
- Модуль володіє всіма хендлами й веде їхній облік; зовнішній код
  отримує ассет і запитує звільнення, але не тримає `AsyncOperationHandle`
- Час життя ресурсів прив'язується до явних областей (сцена, забіг,
  екран меню), а не до випадкового `OnDestroy` того об'єкта, який
  першим щось попросив
- Модуль — звичайний клас з `Initialize()` через `GameBootstrap`, як і
  решта сервісів. Без static, без DI-контейнера

**Чому саме так.** Розкидане завантаження ламається тихо і пізно: хендл,
звільнений двічі, і хендл, не звільнений жодного разу, обидва не дають
помилки в момент помилки. Витік видно як зростання пам'яті через
півгодини гри, а подвійне звільнення — як зникнення чужого ассета в
іншій системі. Одна точка входу перетворює це з полювання на баг у
перевірку одного файлу. Друга причина: коли з'явиться мережа, набір
ресурсів на клієнті й на хості різний, і місце, де це задається, має
бути одне.

**Важливий виняток — ECS-префаби.** Сутності ворогів, projectile-ів,
пікапів потрапляють у світ через **бейкінг** (authoring + `Baker` у
SubScene), а не через Addressables. Там `GetEntity(prefab, ...)` — це
посилання часу бейкінгу, і воно правильне. Addressables у DOTS-частині
стосується завантаження самих SubScene/секцій, а не окремих
entity-префабів. Не переписуй бейкери на Addressables.

Практичний поділ:

| Що | Механізм |
|---|---|
| Entity-префаб (ворог, снаряд, орб) | Baker, `GetEntity` |
| Секція данжу / SubScene | Addressables (або `SceneSystem` для entity-сцен) |
| GameObject-префаб UI, VFX, звук | Addressables |
| Конфіги (`SkillDefinition`, `LootTable`) | Addressables, якщо їх багато і вони потрібні вибірково |

## Інпут: тільки новий Input System

- `UnityEngine.Input`, `KeyCode`, `Input.GetAxis`, `Input.mousePosition`,
  `Input.mouseScrollDelta` — **заборонені**. Проєкт працює з
  `activeInputHandler` у режимі New; будь-який legacy-виклик кине
  виняток у рантаймі, а не впаде на компіляції
- Читання інпуту зосереджене в одному місці (`PlayerInputReader`), яке
  віддає намір (`PlayerMoveIntent`) у світових координатах. Решта коду
  не знає ні про пристрої, ні про камеру — це та сама межа, що й для
  ECS-систем ворогів, і той самий шов під майбутню мережу
- Кросплатформність закладається **біндами, не гілками в коді**: одна
  дія має прив'язки для кількох родин пристроїв. Нова платформа має
  бути рядком біндингу
- `<Pointer>/position` замість `<Mouse>/position` — одна прив'язка
  покриває мишу, стилус і тач
- Дії, створені в коді, володіють нативними ресурсами — `Dispose()`
  в `OnDestroy`
- Інпут виду (зум, поворот камери) тримати окремо від ігрового наміру:
  він локальний і ніколи не має потрапити в те, що поїде на сервер

Поточний стан: дії будуються в коді в `CreateActions()`, без
`.inputactions`-ассета. Це свідомий розмін на користь того, щоб інпут
працював одразу, без ассета, який треба тримати в синхроні. Перехід на
ассет, коли знадобиться UI для перепризначення клавіш, — правка одного
файлу.

## Ключовий архітектурний принцип: server-authoritative-ready

Уся ігрова логіка (вороги, скіли, шкода, лут) будується так, ніби її вже
зараз може виконувати виключно сервер/хост, навіть у single-player режимі:

- ECS-системи логіки НЕ звертаються напряму до `Input`, `Camera.main`,
  чи UI — тільки до даних через компоненти/сінглтони
- Розділяти компоненти на:
  - **"видимі" / presentation** (Position, Rotation, анімаційний стан,
    HP-бар) — майбутні кандидати на `GhostComponent` в NFE
  - **"логічні" / authoritative** (AI-рішення, шлях, кулдауни скілів,
    RNG-роли луту) — залишаються суто серверними, не реплікуються
    напряму (наприклад, `PathPoint` buffer НЕ реплікується — клієнт
    знає лише позицію+напрямок)
- Дії гравця (відкрити сундук, кастувати скіл) моделювати як
  "запит на дію" (клієнт) → "результат дії" (сервер), навіть коли
  клієнт і сервер — той самий процес зараз

## ECS-конвенції

- Доступ до глобальних даних (позиція гравця, налаштування) — через
  **singleton-компоненти** (`SystemAPI.GetSingleton<T>()`), НЕ через
  C# static
- Приклад: `PlayerPositionSingleton` — тепер розширений під кількох
  гравців (список `PlayerId` + позиція кожного); `ChaseTarget` ворога
  вибирає найближчого/найагресивнішого гравця зі списку, а не хардкод
  на одного гравця
- Time-slicing для дорогих операцій (pathfinding, масові AOE/chain
  розрахунки) — ліміт N операцій за кадр як параметр, що виноситься
  в інспектор
- `DamageEvent` — буфер-компонент, куди всі системи шкоди пишуть наміри
  ("нанести X шкоди цій цілі"), а окрема `DamageResolutionSystem`
  застосовує це фінально. Дає гнучкість для ланцюгових ефектів
  (chain after kill, explosion on kill) без плутанини в логіці
- Separation/уникнення зіткнень між ворогами — через spatial hashing
  (`NativeParallelMultiHashMap`), не O(n²) перебір
- Object pooling для VFX-інстансів і projectile-entity — не
  Instantiate/Destroy напряму

## MonoBehaviour / UI-шар конвенції

Без static, без DI-контейнера. Замість цього:

1. **ScriptableObject як shared state / event channel** — основний
   підхід для даних, які читаються з багатьох місць (стан гравця,
   event-канали типу `OnWaveCleared`, `OnPlayerDied`). Патерн:
   "ScriptableObjects as Architecture" (Ryan Hipple)
2. **Явний `Initialize()` через один `GameBootstrap`-скрипт** — для
   сервісних класів з поведінкою (AudioManager, SceneLoader). Bootstrap
   створює/знаходить інстанси і викликає `Initialize()` в правильному
   порядку
3. Дані типу `LootTable`, `SkillDefinition`, `ItemDefinition` — теж
   ScriptableObject, консистентно з підходом вище

**Нюанс:** ScriptableObject — asset у пам'яті, спільний для всіх
інстансів у межах одного процесу. Для реального білда (кожен клієнт —
окремий процес) це нормально. При локальному тестуванні мультиплеєра
в одному Editor-інстансі (напр. через ParrelSync) можливі конфлікти
стану — враховувати при переході на NFE.

## Процедурна генерація данжу

- Room-based генерація (BSP або template-based кімнати), не суцільний maze
- Типи кімнат: бойова, скарбниця, прохідна, boss
- NavMesh перебудовується динамічно після генерації
  (`NavMeshSurface.BuildNavMeshAsync`)
- **Генерація за seed**, синхронізованим між гравцями (закладено з самого
  початку, навіть у single-player, щоб не переробляти пізніше для коопу)

## Скіли та модифікатори

Модель на кшталт PoE (skill + support gems):

- `SkillDefinition` (SO): базовий ефект (projectile/melee/aoe/chain),
  урон, кулдаун
- `SkillModifier` (SO): Chain, AOE radius, Fork, Multicast, Elemental
  conversion тощо
- Конвеєр систем: `SkillCastSystem` → `SkillProjectileSystem` /
  `SkillAOESystem` → `SkillHitSystem` → `SkillModifierPipeline`
  (кожен модифікатор — окрема система/job, що читає/пише `DamageEvent`)

## "Вау"-ефекти (масові вбивства)

- Chain: візуальна лінія між цілями з невеликою затримкою (50-100мс)
  між стрибками для читаності
- AOE: VFX Graph particle burst + легкий screen shake (Cinemachine
  impulse) + hit-stop (30-60мс time-scale freeze)
- Death feedback: ragdoll/dissolve-шейдер, знищення entity з затримкою
- Batch-обробка ефектів, що трапились в один кадр — не окремий виклик
  VFX на кожне влучання
- Camera feedback (zoom punch / chromatic aberration) при масових
  вбивствах за короткий час (>5 за 0.5с)

## Порядок розробки (заведений принцип)

Кожна нова велика система впроваджується ітеративно, невеликими кроками,
з перевіркою продуктивності (FPS з 100+ ворогами) перед переходом до
наступного кроку. Не намагатись реалізувати все одним заходом — спочатку
план/структура файлів, узгодження, потім код частинами.

## Прогресія поверхів данжу (floor progression / risk-reward descend)

- Data-driven через `DungeonFloorConfig` (SO): FloorIndex,
  EnemyDifficultyMultiplier, LootRarityWeights, IsBossFloor,
  RoomCountRange, EnemyDensityMultiplier — складність і лут
  масштабуються множниками, а не хардкодяться на кожен поверх
- Boss floors: `BossEncounterConfig` (SO), boss-кімната блокується
  (`BossRoomState`: Locked/InProgress/Cleared) до перемоги; інтервал
  між боссами — параметр конфігу, не константа в коді

### Смерть/лут — трьохстанова модель (Alive → Downed → Dead), зафіксовано

Правило гри: кожен гравець відповідає лише за свій лут. Смерть
двофазна — спочатку "Downed" (можна відродити), і лише за timeout
(або team wipe) настає "Dead" з остаточною втратою лута.

- `PlayerLifeStateComponent`: enum `Alive/Downed/Dead` + `DownedTimer`
  + `MaxDownedDuration` + `RevivingByPlayer` (Entity.Null якщо ніхто
  не відроджує)
- `DownedStateSystem`: HP <= 0 і Alive → Downed, старт таймера
- `ReviveInteractionSystem`: живий гравець поруч утримує channeled-дію
  відродження; переривається при відході чи отриманні урону тим, хто
  відроджує
- `DownedTimeoutSystem`: таймер сплив без відродження → Dead →
  викликає `DeathResolutionSystem` ЛИШЕ для цього гравця (втрата
  лише його лута, не чужого)
- `TeamWipeCheckSystem`: усі гравці одночасно Downed/Dead (жодного
  Alive) → примусово всіх Downed → Dead, завершує забіг для команди.
  Сам видаленням лута не займається — викликає ту саму
  per-player `DeathResolutionSystem` для кожного, щоб не дублювати
  логіку

### Ризик предметів — `ItemRiskState`, а не `AcquisitionSource`

Ризику підлягає НЕ лише знайдене в підземеллі, а й усе, що гравець
взяв із собою з лобі на цей захід:

```csharp
public enum ItemRiskState
{
    Safe,     // лишається в PersistentStash, недоступне під час забігу
    AtRisk    // взяте на захід (з лобі АБО знайдене в данжі) —
              // втрачається при остаточній смерті (Dead) власника
}
```

При вході в данж екіпіроване з лобі позначається AtRisk. При Dead —
все AtRisk цього гравця видаляється. При успішному виході з данжу —
AtRisk → Safe (конвертація enum, без переносу між колекціями).

### Лобі-фаза

Окремий `LobbyState` перед стартом забігу — гравці екіпірують
персонажа (спорядження, зілля) з `PersistentStash` (Safe-інвентар).
Те, що екіпіровано на момент старту, стає AtRisk на час забігу.

### Кооп-специфічне рішення (закладено, НЕ конфігурований прапорець — рішення прийнято)

- Team wipe відбувається лише як наслідок того, що всі гравці
  досягли стану Dead (немає живого, хто міг би відродити) — не
  окремий bool-прапорець, а емерджентний результат Downed/Revive
  системи
- `DungeonRunState` (singleton, спільний для команди) розширити
  полями `IsRunActive` і `RunEndReason` (TeamWipe /
  AllExtractedSuccessfully), щоб UI та інші системи знали момент і
  причину завершення забігу
